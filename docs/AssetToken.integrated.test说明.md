# AssetToken 联动集成测试说明

## 概述

本文件 (`test/AssetToken.integrated.test.js`) 包含了针对 AssetToken 合约中四个核心函数的联动集成测试：
- `withdrawDividend`: 提取分红和清算金
- `sellShares`: 出售资产份额（创建卖单）
- `cancelOrder`: 取消订单
- `payOrder`: 支付订单（买家购买卖单）

这些测试旨在验证这些函数在实际业务场景中的交互和联动工作是否正确。

## 测试环境设置

### 合约部署
- MockERC20 (USDT) - 支付代币
- CollateralVault - 抵押品金库
- RevenueManager - 收益管理器
- LiquidateManager - 清算管理器
- OrderBook - 订单簿
- AssetToken - 资产代币

### 初始参数
- 资产总价值: 1,000,000 USDT
- 募资金额: 500,000 USDT
- 最大供应量: 1,000,000 代币（18位精度）
- 季度预期分红: 10,000 USDT
- 季度周期: 7天

### 初始持有者
- Seller: 100,000 代币 (10%)
- Buyer: 100,000 代币 (10%)
- Provider: 300,000 代币 (30%)

## 测试场景

### 场景1: withdrawDividend -> sellShares -> payOrder 完整流程

**目的**: 验证从分红提取、创建卖单、到订单成交的完整业务流程

**步骤**:
1. 提供收益并等待产生分红
2. 卖家创建卖单（自动提取分红）
3. 验证卖家收到分红
4. 等待一段时间，让订单期间产生新的分红
5. 买家支付订单
6. 验证：
   - 卖家收到货款 + 订单期间分红
   - 买家收到份额
   - 订单状态正确更新

**关键验证点**:
- sellShares 会自动调用 withdrawDividend
- payOrder 时卖家会收到订单期间的分红
- 买家份额正确增加
- 订单成交数量正确记录

---

### 场景2: sellShares -> cancelOrder 流程

**目的**: 验证卖单的创建和取消流程

**步骤**:
1. 提供收益并等待
2. 创建卖单
3. 验证份额已冻结（frozenAmounts 增加）
4. 等待一段时间
5. 取消订单
6. 验证份额已解冻
7. 验证可以再次提取订单期间的分红

**关键验证点**:
- sellShares 时 ERC20 余额不变，但 frozenAmounts 增加
- cancelOrder 后 frozenAmounts 减少
- 取消订单后的份额会保留订单创建时的时间戳
- 可以正确提取订单期间的分红

---

### 场景3: 多次交易流程

**目的**: 验证卖家多次出售和买家多次购买的场景

**步骤**:
1. 提供收益
2. 第一次卖单 + 成交
3. 验证买家第一次购买后的份额
4. 第二次卖单 + 成交
5. 验证买家第二次购买后的份额
6. 买家提取分红

**关键验证点**:
- 多次交易后份额累加正确
- 每次交易都正确记录 holderInfo
- 买家可以正确提取多次购买后的分红

---

### 场景4: 多轮分红后的交易

**目的**: 验证经历多轮分红后的卖单创建和成交

**步骤**:
1. 第一轮分红
2. 第二轮分红
3. 卖家创建卖单（提取所有历史分红）
4. 第三轮分红
5. 买家支付订单
6. 第四轮分红
7. 买家提取分红

**关键验证点**:
- sellShares 会提取所有历史分红
- payOrder 时卖家收到订单期间的分红
- 多轮分红的累计计算正确

---

### 场景5: 份额合并逻辑验证

**目的**: 验证多个份额持有者之间的交易

**步骤**:
1. 验证初始持有份额
2. 提供收益
3. 卖家提取分红后创建卖单
4. 买家购买并验证份额增加

**关键验证点**:
- withdrawDividend 会合并所有份额记录
- sellShares 会先合并份额再创建订单
- 交易后买家份额正确增加

---

### 场景6: 边界条件测试

**目的**: 验证各函数的参数验证

**测试用例**:
1. withdrawDividend 参数验证:
   - 拒绝零地址作为接收者
   - 拒绝零地址作为持有者
   - 拒绝为无份额的地址提取分红

2. payOrder 参数验证:
   - 拒绝购买数量为0

**关键验证点**:
- 所有边界条件都能正确拒绝
- 错误消息准确

---

### 场景7: 时间戳和分红计算验证

**目的**: 验证各个时间节点的分红计算

**步骤**:
1. T0: 初始时间
2. T1: 提供第一笔收益
3. T2: 创建卖单（提取 T0-T1 期间分红）
4. T3: 提供第二笔收益
5. T4: 订单成交（卖家收到 T2-T3 期间分红）
6. T5: 买家提取分红

**关键验证点**:
- 每个时间段的分红计算正确
- 时间戳正确记录和更新
- 买家刚购买时可能没有分红（因为持有时间短）

## 测试结果

所有7个测试场景全部通过，验证了以下核心功能：

1. **分红提取机制**: withdrawDividend 正确计算和转移分红
2. **卖单创建**: sellShares 正确冻结份额并创建订单
3. **订单取消**: cancelOrder 正确解冻份额并恢复状态
4. **订单成交**: payOrder 正确转移份额和支付款项
5. **时间戳管理**: 各个时间节点的分红计算准确
6. **份额合并**: withdrawDividend 和 sellShares 正确合并多个份额记录
7. **参数验证**: 所有边界条件都能正确处理

## 测试覆盖的业务逻辑

### 分红计算
- 基于时间范围的分红计算
- 多个份额记录的分红累加
- 订单期间分红的正确分配

### 份额管理
- 份额冻结和解冻
- 份额转移
- 份额记录的合并

### 订单流程
- 订单创建
- 订单成交（全部或部分）
- 订单取消
- 订单期间收益的处理

### 时间戳管理
- lastDividendTime 的更新
- lastLiquidationClaimTime 的更新
- holdingStartTime 的设置
- 订单创建时时间戳的保存

## 注意事项

1. **测试顺序**: 测试之间可能存在状态依赖，应按顺序执行
2. **时间控制**: 使用 `time.increase()` 模拟时间流逝
3. **售罄条件**: 所有涉及 sellShares 和 withdrawDividend 的操作都需要满足售罄条件（soldOutTimestamp + 1 day）
4. **精度转换**: 注意 18 位精度（代币）和 6 位精度（USDT）之间的转换
