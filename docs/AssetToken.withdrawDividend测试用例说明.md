# AssetToken withdrawDividend 测试用例说明

## 📋 概述

本文档详细说明了 `AssetToken.withdrawDividend.test.js` 中的所有测试用例。该测试套件验证了 AssetToken 合约中分红提取功能的正确性，包括基本分红、清算金提取、多次购买场景、多持有者场景等。

## 🔧 测试环境设置

### 合约部署

每个测试用例开始前都会部署以下合约：

1. **MockERC20 (paymentToken)**: 模拟 USDT 稳定币
2. **CollateralVault**: 管理抵押金和收益
3. **RevenueManager**: 管理收益记录
4. **LiquidateManager**: 管理清算逻辑
5. **AssetToken**: 资产代币主合约

### 资产参数配置

```javascript
ASSET_NAME: "Test Real Estate Token"
ASSET_SYMBOL: "TRE"
TOTAL_VALUE: 1,000,000 USDT        // 资产总价值
FUNDRAISE_AMOUNT: 500,000 USDT     // 募集金额
MAX_TOTAL_SUPPLY: 1,000,000 代币   // 最大供应量
QUARTERLY_EXPECTED_DIVIDEND: 10,000 USDT  // 季度预期分红
QUARTER_CYCLE_DAYS: 90 天          // 季度周期
```

### 账户配置

- **owner**: 合约所有者
- **buyer1, buyer2, buyer3**: 代币购买者
- **provider**: 资产提供者（负责存入抵押金和收益）
- **recipient**: 分红接收者

## 📚 测试用例详解

## 1️⃣ 基本分红提取功能 (Basic Dividend Withdrawal)

### 1.1 应该能够成功提取分红

**测试目的**: 验证基本的分红提取流程

**测试步骤**:
1. buyer1 购买 10,000 代币（占总供应量的 1%）
2. 等待 5 天
3. provider 向 CollateralVault 存入 5,000 USDT 收益
4. RevenueManager 记录该笔收益
5. 再等待 5 天
6. buyer1 提取分红到 recipient 地址

**预期结果**: 
- recipient 收到的分红金额 > 0
- 分红成功转账到指定地址

**业务意义**: 确保持有者能够正常提取其应得的分红。

---

### 1.2 应该正确计算持有者的分红比例

**测试目的**: 验证分红按持有比例正确分配

**测试步骤**:
1. buyer1 购买 10,000 代币（1% 持有比例）
2. 等待 3 天
3. provider 存入 10,000 USDT 总收益
4. 记录收益并等待 5 天
5. buyer1 提取分红

**预期结果**:
```
实际分红 = 10,000 USDT × 1% = 100 USDT
```

**验证逻辑**:
```javascript
buyerSharePercentage = 10,000 / 1,000,000 × 10,000 = 100 基点 (1%)
expectedDividend = totalRevenue × buyerSharePercentage / 10,000
```

**业务意义**: 确保分红计算精确，持有者获得与其持股比例相符的分红。

---

### 1.3 没有收益时应该不转账

**测试目的**: 验证无收益时的安全处理

**测试步骤**:
1. buyer1 购买代币
2. 不存入任何收益
3. 等待 5 天后尝试提取分红

**预期结果**:
- recipient 余额不变（收到 0 分红）
- 不发生转账

**业务意义**: 防止无效转账，节省 gas 费用。

---

### 1.4 应该更新 lastDividendTime

**测试目的**: 验证提取后时间戳正确更新

**测试步骤**:
1. buyer1 购买代币
2. 等待 3 天，存入收益
3. 再等待 5 天后提取分红
4. 检查 HolderInfo 的 lastDividendTime

**预期结果**:
- `holderInfo.lastDividendTime` 更新为提取时的时间戳
- 时间戳误差在 ±2 秒内

**业务意义**: 确保下次提取时能正确计算增量分红，避免重复提取。

---

## 2️⃣ 清算金提取功能 (Liquidation Withdrawal)

### 2.1 有清算记录时应该能够提取清算金

**测试目的**: 验证清算金提取流程

**测试步骤**:
1. buyer1 购买 10,000 代币（1%）
2. provider 存入 100,000 USDT 抵押金
3. 等待 10 天
4. 存入低于预期的收益（5,000 USDT < 10,000 USDT）
5. 等待季度周期（90 天）
6. 触发清算检查（清算不达标）
7. 再等待 5 天后提取

**预期结果**:
- 清算次数 = 1
- recipient 收到的金额 > 0（包含分红 + 清算金）

**业务意义**: 保障投资者在收益不达标时能获得清算补偿。

---

### 2.2 应该正确计算清算金额

**测试目的**: 验证清算金计算的精确性

**测试步骤**:
1. buyer1 购买 10,000 代币（1%）
2. provider 存入 100,000 USDT 抵押金
3. 触发一次清算（收益不达标）
4. 提取分红和清算金

**预期结果**:
```
总抵押金: 100,000 USDT
单次清算比例: 20%
可清算金额: 100,000 × 20% = 20,000 USDT
buyer1 清算金: 20,000 × 1% = 200 USDT
buyer1 分红: 5,000 × 1% = 50 USDT
总计: 250 USDT
```

**计算公式**:
```javascript
expectedDividend = lowRevenue × buyerSharePercentage / 10,000
expectedLiquidation = liquidatableAmount × buyerSharePercentage / 10,000
expectedTotal = expectedDividend + expectedLiquidation
```

**业务意义**: 确保清算补偿计算准确，投资者权益得到保障。

---

### 2.3 多次清算应该累计清算金

**测试目的**: 验证多次清算的累计效果

**测试步骤**:
1. buyer1 购买代币并存入抵押金
2. 第一次清算：收益 5,000 USDT（不达标）
3. 等待季度周期后触发清算
4. 第二次清算：收益 6,000 USDT（仍不达标）
5. 再次触发清算
6. 提取所有累计的分红和清算金

**预期结果**:
- 清算次数 = 2
- 总收到金额 = 两次分红 + 两次清算金

**业务意义**: 确保多次违约的补偿能够累加，充分保护投资者。

---

### 2.4 没有清算记录时不应该转移清算金

**测试目的**: 验证收益达标时不触发清算

**测试步骤**:
1. buyer1 购买代币并存入抵押金
2. 存入超额收益（15,000 USDT > 10,000 USDT）
3. 等待季度周期后检查
4. 提取分红

**预期结果**:
- 清算次数 = 0
- 只收到分红（150 USDT），没有清算金

**计算验证**:
```javascript
expectedDividend = 15,000 × 1% = 150 USDT
actualReceived = expectedDividend (无清算金)
```

**业务意义**: 确保清算机制不会误触发，只在真正违约时生效。

## 3️⃣ 多次购买场景 (Multiple Purchase Scenarios)

### 3.1 应该合并多个 HolderInfo 记录

**测试目的**: 验证 HolderInfo 合并机制

**测试步骤**:
1. buyer1 第一次购买 5,000 代币
2. 等待 10 天
3. buyer1 第二次购买 5,000 代币
4. 存入收益并提取分红

**预期结果**:
- 提取后，HolderInfo[0] 的 shares = 10,000（两次购买合并）
- 只保留一个活跃的 HolderInfo 记录

**技术细节**:
- `withdrawDividend` 会调用内部的合并逻辑
- 将多个时间段的持仓合并为一个最新记录

**业务意义**: 优化存储，降低 gas 成本，简化数据结构。

---

### 3.2 应该正确计算不同购买时间的分红

**测试目的**: 验证时间加权分红计算

**测试步骤**:
1. buyer1 第一次购买 5,000 代币
2. 存入第一笔收益 5,000 USDT
3. 等待 10 天
4. buyer1 第二次购买 5,000 代币
5. 存入第二笔收益 5,000 USDT
6. 提取分红

**预期逻辑**:
- 第一笔 5,000 代币享受两笔收益
- 第二笔 5,000 代币只享受第二笔收益
- 总分红应该反映不同持有时长

**预期结果**:
- 实际收到的分红 > 0
- 分红金额考虑了持有时长差异

**业务意义**: 公平分配分红，早期投资者获得更多收益。


**验证逻辑**:

**业务意义**: 确保所有持有者按持股比例公平获得分红。

## 🔍 关键技术点

### 1. HolderInfo 合并机制
```solidity
struct HolderInfo {
    uint256 shares;              // 持有份额
    uint256 lastDividendTime;    // 上次提取时间
}
```
- 多次购买会创建多个 HolderInfo
- 提取时自动合并为单一记录
- 优化存储和计算效率

### 2. 分红计算公式
```javascript
分红金额 = Σ(每期收益 × 持股比例 × 持有时长权重)
```

### 3. 清算金计算
```javascript
清算金 = 总抵押金 × 单次清算比例(20%) × 持股比例 × 清算次数
```

### 4. 时间加权
- 使用 `lastDividendTime` 追踪上次提取时间
- 只计算增量区间的分红
- 防止重复提取
