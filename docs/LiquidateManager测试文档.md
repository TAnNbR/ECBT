# LiquidateManager 集成测试文档

## 测试概述

本测试套件对 LiquidateManager 与真实 RevenueManager 合约的集成进行全面测试。测试使用真实的 RevenueManager 合约而非 Mock，以验证完整的业务逻辑流程。

### 测试环境配置

- **RevenueManager**: 真实合约，时间单位设置为小时（HOUR）
- **CollateralVault**: Mock 合约，用于验证跨合约调用
- **季度周期**: 90 天
- **预期季度分红**: 10,000 USDT
- **清算比例**: 20% (2000 基点)

---

## 一、真实 RevenueManager 集成测试（13 个测试）

### 1. 从 RevenueManager 读取累计收益

**测试目的**: 验证 LiquidateManager 能正确读取 RevenueManager 的累计收益数据。

**操作流程**:
- 通过 RevenueManager 记录三次收益：3000、4000、5000 USDT（间隔 1 小时）
- 验证 RevenueManager 累计收益为 12,000 USDT
- 执行季度收益检查

**验证点**:
- 清算次数为 0（达标）
- LiquidateManager 记录的收益值与 RevenueManager 一致
- liquidationTimes 数组长度为 0（达标时不记录）

---

### 2. RevenueManager 收益不足时应触发清算

**测试目的**: 验证当收益低于预期时，系统正确触发清算机制。

**操作流程**:
- 记录三次收益：2000、1500、1500 USDT（间隔 1 小时）
- 累计收益为 5,000 USDT，低于预期的 10,000 USDT
- 执行季度收益检查

**验证点**:
- 清算次数增加到 1
- CollateralVault 的 updateLiquidatableCollateral 被调用
- 调用参数为 2000（20%）

---

### 3. 跨季度累计收益计算应该正确

**测试目的**: 验证跨多个季度的收益差值计算逻辑正确性。

**操作流程**:

**第一季度**:
- 记录三次收益，每次 5000 USDT，累计 15,000 USDT
- 检查结果：季度收益 = 15,000 - 0 = 15,000（达标）
- lastRecordedRevenue 更新为 15,000

**第二季度**:
- 等待 90 天
- 记录三次收益：3000、2500、2500 USDT
- 累计收益达到 23,000 USDT
- 检查结果：季度收益 = 23,000 - 15,000 = 8,000（不达标）
- 清算次数增加到 1

**第三季度**:
- 等待 90 天
- 记录三次收益，每次 4000 USDT
- 累计收益达到 35,000 USDT
- 检查结果：季度收益 = 35,000 - 23,000 = 12,000（达标）
- 清算次数保持为 1

**验证点**:
- 每个季度的收益计算基于累计差值
- 达标时清算次数不增加
- 不达标时清算次数累加

  - +30 分钟：3000 USDT

- 所有记录都会被截断到同一个整点小时

**验证点**:

- 截断后的时间戳被正确标记
- LiquidateManager 检查时能正确读取累计值
- 收益刚好达标，清算次数为 0

### 11. 连续达标时周期检查行为

**测试目的**: 验证连续达标情况下的周期控制行为。

**操作流程**:

**第一次检查**:
- 记录 12,000 USDT（达标）
- 清算次数为 0，liquidationTimes 为空
- lastRecordedRevenue = 12,000

**第二次检查**:
- 等待 90 天
- 记录额外 3,000 USDT，累计 15,000
- 季度收益 = 15,000 - 12,000 = 3,000（不达标）

**验证点**:
- 第一次达标时不记录清算时间
- 第二次检查时仍需等待周期（因为 lastCheckTime 从 liquidationTimes 获取，为空时从 0 开始计算，但测试网络时间戳足够大）
- 第二次不达标，清算次数增加到 1

### 12. 不达标后再达标需要等待周期

**测试目的**: 验证不达标后的周期限制机制。

**操作流程**:

**第一次检查**:
- 记录 5,000 USDT（不达标）
- 清算次数为 1
- 清算时间被记录到 liquidationTimes

**立即第二次检查**:
- 尝试立即检查，预期失败
- 错误信息："Quarter cycle not completed"

**等待 90 天后检查**:
- 等待 90 天后可以执行检查
- 记录额外 10,000 USDT，累计 15,000
- 季度收益 = 15,000 - 5,000 = 10,000（达标）
- 清算次数保持为 1

**验证点**:
- 不达标会记录清算时间
- 下次检查必须等待 90 天
- 达标后清算次数不增加

## 测试总结

**总测试数量**: 19 个  
**测试通过率**: 100%  
**测试执行时间**: 约 2 秒

### 核心测试覆盖点

1. **跨合约集成**: 验证 LiquidateManager 与 RevenueManager 的数据交互
2. **累计收益计算**: 验证季度收益差值计算的正确性
3. **清算触发机制**: 验证达标与不达标的判定逻辑
4. **周期控制**: 验证 90 天周期限制的实现
5. **时间戳处理**: 验证 RevenueManager 的时间截断功能
6. **索引查找**: 验证 IndexBitmap 的查找功能集成
7. **边界情况**: 验证 0 值、等于预期、超大值等边界条件
8. **事件系统**: 验证所有关键事件的触发和参数
9. **性能基准**: 建立 Gas 消耗的性能基准
10. **业务流程**: 验证多季度复杂场景的完整业务逻辑

### 关键发现

- **周期控制机制**: lastCheckTime 从 liquidationTimes 数组获取，只有不达标时才记录
- **达标判定**: 使用 >= 运算符，刚好等于预期值也算达标
- **累计计算**: 每次检查都会更新 lastRecordedRevenue，无论是否达标
- **Gas 效率**: 100 次历史记录情况下，检查操作 Gas 消耗约 79,227，表现良好
